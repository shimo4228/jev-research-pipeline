# ノートの読み面を本文だけにする — 付録の折りたたみと見出しの階層（2026-10-04）

著者の指摘（2026-10-04）: 本文は読みやすくなったが、Claims などの付録が本文の下に並んで読みにくい。
本文の生成の仕組みは変えず、付録を洗練し見出しの可読性を上げる。評価しながら改善する。

## 出発点（2026-10-04 の実測）

- vault の jrp ノート 54 本で、著者のチェック 19 件はすべて `jrp:qday`（読む価値があった）。
  `## Review`（`jrp:source`）と Claims（`jrp:claim`）へのチェックは 0 件
- `> [!note]- Claims` の直後に空行があり（`render_report` が parts を `"\n"` で連結し、
  `_bullets` の出力と callout 見出しの間に空行が入る）、Obsidian では callout が空のまま閉じて
  claim 行は折りたたまれない普通の引用として見えている
- 中身が空の欄が `(なし)` で毎回出る（ans 10/4: 橋渡し・Claims・未判定の 3 つ）
- 問いの見出しが `###`、付録が `##` — アウトラインで付録の方が上位に見える。
  「今日の変化」「証拠」は見出しでなく地の文
- `## 運用` は 30 行前後で、ノートの末尾の半分を占める

## 方針

- 読み面 = 問いごとの見出し・本文・証拠・反証・「読む価値があった」チェック。それ以外
  （Review / 橋渡し / Claims / 未判定 / 運用）は、閉じた callout にまとめる。callout の中に
  空行を入れない。callout は入れ子にしない（harvester の `_MARK_LINE_RE` は `>` 1 段まで）
- 空の付録欄は出さない
- 見出しの階層: 問い = `##`、その下の小見出し = `###`。具体形は下の評価で選ぶ
- 変えないもの: 本文の生成（プロンプト・モデル・判定）、3 種の `<!-- jrp:… -->` 行の形、
  frontmatter、`_fitted` の切り詰め順

## 評価

候補 V0（現行）/ V1（折りたたみの修正と空欄の削除だけ）/ V2（V1 + 見出しの階層 + 証拠の題名をリンクに）/
V3（V2 から「今日の変化」の見出しを外す）を、10/1〜10/4 の実ノートを描き直して比べる。

- 機械の指標: 開いた直後に見える部分のうち読み面の割合 / `(なし)` の数 / 全 mark の harvest
  往復（描き直す前後で同じ mark 集合が拾える）/ callout 内の空行 0
- 見た目: Obsidian の描画を HTML で近似（callout → 閉じた `<details>`）し、スマホ幅と PC 幅で撮る。
  案の名前を伏せて fresh-context の判定役に渡し、決まった課題（問いの数と題を最初の画面で言えるか、
  2 つ目の問いのチェックはどこか、本文でないものが見えているか）と「一番読みやすいのはどれか・なぜか」を聞く
- 受け入れは著者の読み比べで決める（scratchpad に比較ファイル）

## Goal

  mark の harvest 往復、見出しの階層）
- docstring・`docs/scheduling.md`・design に今回の判断を同じ diff で反映する
